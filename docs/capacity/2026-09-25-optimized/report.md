# 容量瓶颈优化与复测（2026-09-25）

针对 [首次容量报告](../2026-09-23/report.md) 中的热榜重建超时与 Outbox 积压，完成了查询、刷新、投递及连接复用优化。历史报告与失败数据保持原样。

结果：热榜 100 RPS 复测零错误，最终 P95 8.5ms；同步评论 100 RPS 的 P95 为 938ms，但仍有 59.4% 请求使用同步回退；纯异步 50 RPS 三分钟全部完成且未见持续积压。纯异步 100 RPS 仍有积压增长，不能宣称该档位已稳定通过。

## 实现变化

**热榜：在数据库内完成聚合、排序和前 K 条截取。** 旧实现将窗口内全部分钟/视频分组搬到 Go，再创建临时 Redis 桶、合并并全量读回。新实现直接复用单条权威 SQL，只返回默认 2000 条。窗口仍为 `(asOf - HotWindow, asOf]`，有效点赞 × 3、评论 × 5，同分按视频 ID 降序；撤销、删除、自然过期及未来视频过滤保持原语义，持久化快照和 Redis 分页缓存也保持原语义。

实时事件分钟桶仍按事件 ID 去重，但不是权威快照来源。此次取消了全量分钟桶重建与 ZUNIONSTORE 中间步骤，不把保留的增量桶表述为已经实现了完整增量排名。每个新快照仍需 SQL 聚合，数据规模进一步上升仍需另行评估。

**Outbox：有界批量发布与连续排空。** 从每 600ms 取 20 条、逐条确认和更新，改为每批最多 128 条流水发布，核对全部确认序号后单次更新数据库。有积压时立即取下一批，空闲时等待 100ms。关闭确认流、NACK、路由退回或超时不标记该批成功，重连后允许整批重试，由事件/命令幂等处理重复。批次 5 秒超时通过连接关闭中断底层阻塞写入，因为本地 AMQP 库的 `PublishWithContext` 不响应 context。

**刷新等待和命令并发：** 第一轮复测发现热榜 100 RPS 的 P99 仍受同步刷新影响，评论 100 RPS 仍频繁同步回退。首屏改为在后台刷新期间使用有效上一快照，生成时间最多允许距现在两个刷新周期（默认两分钟），且不能超过快照自身期限；冷启动或超过宽限仍需获取新快照。API 命令发布改为固定四路独立连接，确认后尝试标记对应 Outbox，减少重复发送；标记失败时保留安全重试。Worker 消费者从 2 个调整为 4 个，每个预取仍为 4。

**连接复用与轮询压力：** 中间轮次的 MySQL CPU 接近两核配额，累计创建连接超过两万，虽然 Outbox 较小，RabbitMQ 仍出现积压。数据库空闲连接从 4 调整到与既有最大连接上限一致的 16，空闲五分钟后回收，最大连接数仍为 16。命令等待从固定 40ms 查询改为 40、80、160、200ms 的有界退避，700ms 的同步等待预算保持不变。

仍采用至少一次投递；没有关闭持久化、发布确认、限流或数据一致性检查，也没有增大容器资源配额。并发调整会增加连接和数据库竞争，超出本轮档位仍需继续测量。

## 正确性验证

完整 `go test -race -count=1 -v ./...`：第一轮 24 项通过，最终版本 25 项通过，无跳过，无 race 报告。新增批量发布测试覆盖确认丢失时保留待发送状态、128 条确认后统一标记、重复执行的持久化去重；新增快照测试验证数据库不可用时仍能提供有效上一快照，但超过刷新宽限或快照到期后拒绝返回它。已有测试覆盖 Broker 断开重连、异步命令与同步回退、滚动窗口过期/删除、固定快照分页与 Redis 丢失恢复。热榜测试直接核对期望分数，避免将同一实现与自己比较。

最终日志见 [refined-tests.log](refined-tests.log)，中间轮次见 [final-tests.log](final-tests.log)，第一轮见 [tests.log](tests.log)。`go vet ./...` 和 Linux 构建通过。

## 复测条件

同一主机与 `compose.capacity.yml` 资源配额、同一压测器和到达速率模型。由于相隔两天，旧互动已移出 24 小时窗口且会话已过期，使用 `compose.capacity.retest.yml` 的新专用卷重新生成相同规模和相对时间分布：1 万用户、10 万视频、60 万点赞、30 万评论、10 万关注。旧数据卷未修改。

这是相同生成规则的可比复测，不是逐行相同数据时刻的严格 A/B 实验；不据此宣称精确提升倍数。压测前关闭独立集成测试容器。服务与发压器仍共享物理机，未加入媒体 I/O、TLS、反向代理或公网流量。

测试中途因工具自动审批额度问题暂停，恢复后继续测试。数据生成于北京时间 15:42:43，`stable-async-50` 于 20:34:54 开始，`refined-hot-100` 于 20:37:58 开始，距生成已约五小时。因此最后两档的窗口内历史互动自然减少，另有先前压测新增评论；它们不能与早期档位当作完全相同热度数据量的严格对照。早期同规模新鲜数据上的 `final-hot-100` 已单独通过三分钟跨刷新测试（P95 8.3ms / P99 10.1ms）。

```powershell
docker compose -f compose.capacity.yml -f compose.capacity.retest.yml up -d --wait api
.tools/capacity/loadgen.exe -mode seed
docker compose -f compose.capacity.yml -f compose.capacity.retest.yml up -d --wait worker
python -X utf8 scripts/capacity/run.py --scenarios hot,write --rates 20,100 --duration 90s --label optimized --output docs/capacity/2026-09-25-optimized
python -X utf8 scripts/capacity/run.py --scenarios hot,write,async --rates 100 --duration 3m --label final --output docs/capacity/2026-09-25-optimized
python -X utf8 scripts/capacity/run.py --scenarios write,async --rates 100 --duration 3m --label refined --output docs/capacity/2026-09-25-optimized
python -X utf8 scripts/capacity/run.py --scenarios async --rates 50 --duration 3m --label stable --output docs/capacity/2026-09-25-optimized
python -X utf8 scripts/capacity/run.py --scenarios hot --rates 100 --duration 90s --label refined --output docs/capacity/2026-09-25-optimized
```

`seed` 必须在空数据库执行，拒绝覆盖已有数据。最终二进制和源码哈希见 [refined-environment.json](refined-environment.json)，中间轮次见 [final-environment.json](final-environment.json)，第一轮见 [environment.json](environment.json)，数据生成时间见 [fixture.json](fixture.json)。`optimized-*` 为第一轮实现，`final-*` 为加入后台刷新、发布池、四消费者及确认后标记的中间实现，`refined-*` 和 `stable-*` 为继续加入连接复用与轮询退避的最终实现。阶段间保留新增评论，未重置数据或缓存来掩盖积压。

同步评论 100 RPS 的 18000 条全部完成，其中 Worker 7305 条、同步回退 10695 条（59.4%）。命令采样峰值 114、Outbox 峰值 20，结束清空。它验证了当前回退机制参与时的服务能力，**不代表 Worker 单独能稳定完成 100 条/秒**。

异步评论 100 RPS 的命令积压从零增长，采样峰值 555，结束后约 4.6 秒数据库待处理记录清空，最终 18000 条全部完成。与中间轮次相比完成延迟有所下降，但仍未达到“不持续积压”的目标。

50 RPS 是本轮验证过的纯异步稳定候选档位，仍只覆盖三分钟本地测试。该档命令积压采样峰值 2、Outbox 峰值 6，9000 条全部成功完成。不能外推生产最大 QPS、长时间稳态容量或完整混合负载。所有业务完成延迟均为服务器命令 `created_at → completed_at`，不是客户端从发送到观察完成的完整端到端延迟。

本轮共 11 个阶段、129600 次请求，HTTP 错误和调度丢弃均为零；这不代表所有档位满足延迟及积压目标。全部阶段计数关系与积压采样已校验，无监控查询错误。完整计数及资源采样见 [原始测量汇总](measurements.md)。

最终检查：累计 91800 个压测命令完成、失败为零，待处理命令和 Outbox 均为零；RabbitMQ 主队列、重试、死信的待消费及未确认均为零，见 [数据库状态](final-snapshot.json) 与 [队列状态](final-rabbitmq.json)。资源采样包含排空期，只能作为当前单机条件的证据。数据库累计连接计数包括健康检查、暂停期间和诊断连接，不能直接据此计算每请求连接成本或孤立归因。结束时额外窗口行数查询未选择数据库而失败，未将它作为数据量证据。

测试容器和网络已关闭，新旧专用数据库卷均保留。未部署生产、未提交或推送代码。后续要验证更高的纯异步容量，应针对数据库提交开销、消费者吞吐及通知与命令共享队列继续分析，不能靠提高受理速度或放宽超时宣称通过。
