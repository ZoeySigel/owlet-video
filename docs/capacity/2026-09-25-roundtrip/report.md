# 数据库往返优化（2026-09-25）

本轮继续处理 [上一轮](../2026-09-25-optimized/report.md) 的纯异步 100 RPS 积压与同步回退问题，保持容器 CPU/内存配额、连接上限、消费者数量和持久化设置不变。

## 修改

- 在支持的 UTF-8 配置下启用 MySQL 驱动参数编码，避免一次性查询的 prepare/execute/close 往返。业务仍通过 GORM 参数传值，不手动拼接用户输入。非 UTF-8 编码默认保留预处理，显式 `interpolateParams=false` 可关闭优化，不兼容配置拒绝启用。
- 评论返回值复用同一事务内已加锁读取的用户，以及插入后已生成 ID 的评论对象，省去两次重复查询。时间戳先截到数据库毫秒精度，测试核对返回值与数据库一致。
- 当前执行的命令复用事务中生成的事件载荷，提交后不再查询刚写入的 Outbox。重复命令仍能从持久化 Outbox 读取载荷，修复缓存；事件去重与事务提交语义不变。

## 正确性验证

包含新评论回归的完整 `go test -race -count=1 -v ./...` 通过（26 项）。补充字符集启用策略后，定向 `-race` 测试再次通过：8 种 DSN 配置，以及真实数据库中的中文、emoji、引号、反斜杠、问号、百分号、空字符和 SQL 片段正文。验证保存值、返回值、事件载荷一致，返回作者不含密码哈希，重复命令只创建一条评论。

日志见 [完整回归](roundtrip-tests.log) 与 [参数编码定向回归](roundtrip-encoding-tests.log)。没有升级依赖版本。`go vet ./...` 和 Linux 构建通过。

## 近时对照

使用保留的上一轮二进制和相同 `compose.capacity.yml` / `compose.capacity.retest.yml` 数据卷。先跑旧版纯异步 100 RPS 三分钟，等待命令与消息排空，再重启 API/Worker 切换新版。数据库不重置，新版承受此前测试新增的评论。运行时热度窗口继续推进，因此仍不是完全相同数据时刻的严格 A/B 实验，不宣称精确提升倍率。二进制及源码哈希见 [builds.json](builds.json)。

旧版开始时，窗口内有效点赞 241024 条、评论 212312 条，见 [起始数据库记录](baseline-before.txt)。这些与初始 fixture 的总行数不同，因为历史互动会自然过期。

本轮旧版基线在 3 分钟发压及最多 30 秒排空后，17998 个受理命令只完成 8749 个，另有 2 次调度丢弃，触发超过 5000 条命令积压的停止阈值。该状态与上一轮结果不同，启动期间数据库磁盘读取和日志等待较多，因此不能把两个时段的结果混为同一环境状态。

旧版之后继续自然消费，切换前 [before-recovery.json](before-recovery.json) 已记录命令和 Outbox 为零。名为 `recovery.json` 的 30 秒低速读取实际上没有继承命令积压，不能将旧版剩余命令的完成归功于新版。`baseline-after.txt` 的计数覆盖旧版发压和后续自然排空，不是仅发压窗口。

SQL 驱动准备次数与请求延迟分别记录：降低 prepare 次数只能证明对应开销消除，最终优化效果还需看业务完成延迟和积压，不能用 202 受理速度替代。

## 结果

三个阶段均为纯异步评论 100 RPS、发压 180 秒、最多排空 30 秒，均从零命令积压开始。HTTP 202 表示已受理，不表示业务完成。

| 阶段 | HTTP 成功/计划 | 受理 P95 / P99 | 结果查询时完成/受理 | 最后采样命令积压 |
| --- | --- | --- | --- | ---: |
| 旧版 | 17998/18000（调度丢弃 2） | 418.4 / 721.6 ms | 8749/17998 | 9309 |
| 本轮代码 | 18000/18000 | 1321.4 / 3575.7 ms | 9269/18000 | 8802 |
| 本轮代码 + 组提交实验 | 18000/18000 | 264.8 / 577.4 ms | 10926/18000 | 7154 |

最后一次积压采样早于完成结果查询，因此两列不能直接相减。完整时序见 [原始测量汇总](measurements.md) 及对应 JSON。未完成命令存在时，完成延迟分位数只代表已完成子集。

**本轮没有证明持续写入容量提升，100 RPS 仍不通过。** 新版去除了查询往返，但受理尾延迟在此次运行中反而更高；不能仅凭少量完成数增加宣称整体优化成功。同步 100 RPS 后续阶段因积压保护阈值未执行，本轮也没有重新确认上一轮 50 RPS 档位。

旧版 SQL `Com_stmt_prepare` 从 303 增至 322422；新版从 322436 增至 322437（含压测器查询），证明预处理往返基本消除。计数包含各阶段自然排空，不能用作单位时间吞吐对比。

## 日志提交诊断与实验

[诊断记录](durable-commit-diagnostics.txt) 显示 redo 日志及 binlog 的同步相关等待明显高于实际写入耗时。结合容器 CPU 未达到配额，推测当前瓶颈主要在事务提交与存储路径；这不等于已证明物理磁盘故障，也不能排除消费者共享队列等因素。

实验仅在隔离压测库动态设置 `binlog_group_commit_sync_delay=10000`（10ms）和 `binlog_group_commit_sync_no_delay_count=8`，保持 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`。该设置让并发事务合并同步，但也会增加等待，应按实测选择，见 [MySQL 官方说明](https://dev.mysql.com/doc/refman/8.4/en/replication-options-binary-log.html#sysvar_binlog_group_commit_sync_delay)。

实验改善了本次受理延迟与完成数，但命令仍持续积压，未写入应用或 Compose 默认配置，也没有使用 `SET PERSIST`。保留代码中的重复查询消除与安全参数编码；不将本轮实验包装成已解决写入瓶颈。

下一阶段应对命令执行和通知消费分别统计事务耗时，评估分队列及有界并发，并在固定数据快照、充分预热的环境重复对照；事务批处理需要先验证幂等、失败隔离和崩溃恢复，不能只为提高压测数字取消持久化。
