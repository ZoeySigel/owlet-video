# 本地容量实测（2026-09-23）

本轮是单机容量摸底，不是生产容量认证。缓存命中读取表现较好，但热榜在本数据规模下不可用，写入的 Outbox 投递也存在明确吞吐瓶颈。因此不能把项目描述为“所有亮点均已通过高并发验证”。本轮保留业务实现和限流配置，只新增隔离环境、压测工具、数据与报告。

## 环境与方法

- Ryzen 7 6800H，8 核 16 线程，主机内存约 15.2 GiB；Docker Desktop Linux 虚拟机约 7.36 GiB 内存。压测器与服务共享物理机资源。
- API：2 CPU / 512 MiB；Worker：1 CPU / 512 MiB；MySQL：2 CPU / 1536 MiB；Redis：0.5 CPU / 256 MiB；RabbitMQ：1 CPU / 768 MiB。
- 初始数据：1 万用户、10 万视频元数据、60 万点赞、30 万评论、10 万关注。互动时间分布在约 48 小时内，测试期间继续写入评论。
- 固定到达速率，最多 512 个在途请求；槽不足或调度迟到超过 100ms 计为丢弃。丢弃代表目标流量没有发出，不能从成功请求中排除后宣称达标。
- 预设筛选目标：读取 P95 ≤ 200ms、P99 ≤ 500ms；同步评论 P95 ≤ 1s；错误率 < 0.1%；零丢弃；命令及 Outbox 不持续积压。
- 30 秒逐档筛选后，等待积压自然清空，再运行独立低速异步和混合负载。阶段之间不清数据库或缓存，因此随机详情并非纯冷缓存测试。

原始数据及逐阶段计数见 [测量汇总](measurements.md)，硬件和构建标识见 [环境记录](environment.json)，执行方法见 [复现说明](../README.md)。

## 稳态验证

异步评论从零积压开始，以 10 RPS 运行 120 秒，1200 次请求全部返回 202，1200 个操作最终成功完成，零错误、零丢弃。受理响应 P95 / P99 为 52.3 / 54.4ms；命令持久化到完成 P95 / P99 为 54 / 58ms。停止发压后约 1 秒 Outbox 清空。202 与最终完成分别计数，命令处理时间不等同于完整客户端端到端延迟。

混合负载从零积压开始，以 100 RPS 运行 10 分钟（北京时间 20:36:10–20:46:10），60000 次请求全部成功，零错误、零丢弃、零 429。整体 P95 / P99 为 55.0 / 65.6ms。本模型为 30% 热点详情、20% 分散详情、20% 最新 Feed、20% 点赞榜、10% 同步评论，**不包含滑动窗口热榜**。

| 混合负载内接口 | 请求数 | P95 / P99 ms |
| --- | ---: | --- |
| 热点详情 | 18000 | 2.3 / 3.5 |
| 分散详情 | 12000 | 6.4 / 7.6 |
| 最新 Feed | 12000 | 6.9 / 10.4 |
| 点赞榜 | 12000 | 8.7 / 14.0 |
| 同步评论 | 6000 | 71.0 / 85.1 |

6000 条评论命令全部由 Worker 成功完成，没有进入同步回退；命令持久化到完成 P95 / P99 为 29 / 37ms。Outbox 采样从 0 开始、峰值 12、最终为 0，停止发压后约 1 秒排空；无监控查询错误。RabbitMQ 期间抽样为 0 条待消费、1 条未确认，结束检查各队列的待消费和未确认均为 0，重试和死信也为 0。详见 [混合负载原始结果](steady-mixed-100.json)、[最终数据库状态](final-snapshot.json)、[最终队列状态](final-rabbitmq.json)。

该混合模型在本机本次 10 分钟内满足预设目标，可作为后续回归的基线；不是系统全功能容量上限，也不是长期稳定性认证。热榜刷新在此期间依旧超时。

资源采样共 86 组：API CPU 最高 41.4%、内存最高约 27.1 MiB；Worker CPU 最高 59.0%、内存约 42.1 MiB；MySQL CPU 最高 130.8%、内存约 1272 MiB；Redis CPU 最高 15.7%；RabbitMQ CPU 最高 101.8%。这些是采样最大值，不是完整时间序列的绝对峰值；RabbitMQ 瞬时 CPU 接近配额，不能只凭 API CPU 较低推断整体尚有多少容量。

## 已定位问题与修复优先级

1. **热榜快照重建需要优先优化。** Worker 日志反复显示 `hot_buckets.go:56` 的分钟/视频 SQL 聚合在约 3.6 秒预算内超时。当前路径每次重建都读取大量历史互动分组，再构造 Redis 桶；实时事件桶并未消除这一重建成本。本轮数据规模下，即使低请求率也无法获取可用热榜。下一步应缩小重建数据量、使用可校准的增量聚合或预聚合，并分别验证精确窗口边界与恢复正确性；单纯增加请求并发不能解决它。
2. **Outbox 投递有配置级瓶颈。** `worker.go` 每 600ms 最多扫描 20 条，并逐条等待发布确认与更新数据库。单循环理想上限约 33.3 条/秒；评论路径生成命令和通知事件两条 Outbox，因此理想折算约 16.7 条评论/秒，实际还受确认与数据库开销影响。恢复过程中观测到约 33 条/秒的下降速度，与这一配置一致。应优化批次、确认方式与投递并行度，同时保留幂等和失败重试验证。
3. **分散详情和高档列表需要进一步剖析。** 分散详情 300 RPS 已出现 `video_temporarily_unavailable`；最新 Feed 2000 RPS、点赞榜 1000 RPS 延迟和丢弃明显上升。连接池、回源并发限制、缓存失效和 CPU 配额都应纳入后续分析，本轮不能把其中某一项断言为唯一根因。

本轮未修改这些业务瓶颈，因此报告没有“优化前后提升倍数”。

## 证据与限制

- 各阶段 JSON 保存响应状态、错误样本、调度丢弃、分接口分位数、命令完成情况和每 5 秒数据库积压快照；资源 JSONL 约每 6–7 秒采样一次。
- Docker CPU 百分比按一个逻辑 CPU 为 100% 解释；资源采样覆盖发压和排空期，汇总均值不能当作纯发压均值。积压是离散采样，短暂峰值可能漏采。
- `worker-tail.log` 保存超时证据。CPU 抽样未覆盖具有代表性的热榜构建，MySQL 摘要也未覆盖应用全部预处理 SQL，因此不能用这些诊断附件证明具体 CPU 热点或完整查询占比。
- 本轮不测注册/登录/刷新、上传/视频带宽、TLS、代理、公网、长连接、深分页、多节点故障转移及生产故障演练。视频为占位元数据，历史互动是合成分布；不能外推真实用户规模、DAU 或线上可用性。
- 实测版本来自有未提交修改的工作区，基础提交和 API 二进制 SHA256 已留档；不是该 Git 提交的纯净构建。稳态阶段压测器只增加进度输出，其 SHA256 单独记录。
