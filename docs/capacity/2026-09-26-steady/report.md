# 持续容量、过载保护与故障恢复验收

## 范围与环境

本轮使用 `compose.capacity.yml` 与 `compose.capacity.soak.yml`，专用数据卷 `owlet-capacity-soak-20260926`。此前两轮数据卷保留。新 fixture 为 1 万用户、10 万视频、60 万点赞、30 万评论和 10 万关注；2026-09-26 12:40–12:41（北京时间）生成，互动时间分布覆盖过去 48 小时。

资源配额保持 API 2 CPU/512MiB、Worker 1 CPU/512MiB、MySQL 2 CPU/1536MiB、Redis 0.5 CPU/256MiB、RabbitMQ 1 CPU/768MiB。负载发生器仍与 Docker Desktop 共用物理机。严格持久化保持开启，没有延迟组提交调参。此次并非生产服务器验收，不包含媒体传输、公网、TLS 或登录密码验证。

API 二进制 SHA256：`F484AC7BA720FFCC88E6E448CE9ABD01FF31CE261230941073B2C702E2E526B0`。

源文件与配置哈希见 [builds.json](builds.json)。[查询计划](admission-query-plans.txt) 确认命令及 Outbox 压力检查都使用对应复合覆盖索引。

## 本轮改动

- 互动入口每 API 进程 20 RPS、突发 20、最多 16 在途；现有每用户限流继续生效。
- 共享数据库命令/Outbox 积压达到 200 或最老记录超过 10 秒时暂停写入；检查失败时也暂停，避免故障期间无限接单。查询使用复合索引和有界结果，缓存 1 秒，因此阈值是软上限。
- API 每 5 秒检查，无请求时也能发现异常；状态变化及持续异常写日志，`/healthz.writes` 暴露状态、采样时间、截断积压、最老年龄及累计拒绝数。监控适配器将异常转换为非零退出码。通知渠道需部署环境接入。
- 拒绝发生在创建命令之前，返回 429 或 503 与 `Retry-After`；命令提交增加数据库超时预算。

## 正确性验证

真实 MySQL/Redis/RabbitMQ 下原有 27 项测试完整 `-race` 回归通过；新增 2 项 `-race` 测试验证并发预算、积压拒绝不落库、Outbox 阈值、检查失败关闭入口及恢复。日志保留在本目录。测试依赖在正式长测前关闭。

## 持续写入

先以 20 RPS 预热 60 秒：1200/1200 成功，无错误和调度丢弃，受理 P95 86.3ms、P99 126.5ms。之后单独运行 30 分钟纯异步评论，持续记录实际业务完成、积压、资源与健康状态；最终结果见后续实测表。

30 分钟阶段 **36000/36000 全部受理并完成，零错误、零调度丢弃、零命令失败**。受理 P95/P99 为 **104.5/221.8ms**；命令写入数据库至业务完成的 P95/P99 为 **67/174ms**，最大 783ms（不是完整客户端端到端延迟）。命令积压采样峰值 13，Outbox 峰值 15，结束均为零；RabbitMQ ready/unacknowledged/死信也均为零，见 [队列核验](steady-queues.txt)。

267 次健康采样均正常，无连接错误或入口拒绝。资源采样峰值内存：API 3.84%、Worker 3.05%、MySQL 77.86%、Redis 10.97%、RabbitMQ 23.02%，均相对于各自配额。MySQL 内存从约 810MiB 增至 1.166GiB；30 分钟未触顶，但不能据此证明长期内存完全稳定。完整数据见 [健康与资源摘要](steady-health-summary.json)、[测量汇总](measurements.md) 和原始 JSON。

这支持当前测试配置下的 **20 RPS 纯评论写入运行档位**，不是性能极限或生产承诺。入口上限设为 20 RPS，正常规划流量建议留余量，例如 15 RPS；更高档位、多副本、生产规格及混合业务需另外验证。

## 故障验证

`scripts/capacity/faults.py` 只控制本轮独立 Compose 项目，在持续写入期间分别停止 Worker、Redis、RabbitMQ 和 MySQL，再恢复。保留操作时间、HTTP 结果、积压采样及 RabbitMQ 队列状态。故障阶段的拒绝与不可用应如实记录，不计为无故障持续容量。

前三项各发送 1800 次请求：Worker 故障阶段 1548 次受理、252 次 503，命令积压峰值 209；Redis 故障阶段 1800 次全部受理；RabbitMQ 故障阶段 984 次异步受理、119 次同步回退成功、697 次 503，Outbox 峰值 240。所有已创建命令最终完成，三项恢复后的队列和死信均为零。209/240 超过阈值 200 是一秒采样缓存及在途请求造成的软上限超调，不能宣称严格上限为 200。

初次 MySQL 故障测试发现真实缺陷：1800 次请求中，907 次受理，341 次误报 401，237 次无 HTTP 响应，315 次 503，受理之外的请求延迟 P95 达 10 秒。907 条已受理命令全部完成，数据恢复通过，但错误语义和等待时间不通过。原始失败结果保留为 `fault-mysql-async-20.json`。

随后修复会话查询：数据库回源受 `DB_TIMEOUT` 约束；数据库错误返回可重试的 `503/auth_unavailable`，只有失效凭据/会话返回 401。新增 TCP 接受连接但不完成 MySQL 握手的测试，75ms 查询预算在约 80ms 内返回 503，无效令牌仍返回 401。

**版本边界：上述 30 分钟长测及初次四项故障测试使用原保护版本。鉴权修复构建随后另行执行完整回归、MySQL 故障复测、过载与正常负载复测；不将前一次 30 分钟结果冒充修复后版本的同次测量。**

鉴权修复构建 SHA256 为 `601a30893b81388b04f050ed771fb9bb1516e350e7444240468eccf484d4921b`，源码哈希见 [authfix-build.json](authfix-build.json)。最终完整回归 **30 项通过、0 跳过**，含真实依赖与 `-race`，`go vet ./...` 通过，见 [最终回归日志](final-regression.log)。

MySQL 故障复测：1800 次请求中 **906 次 202、894 次 503，没有 401、没有无 HTTP 响应、没有调度丢弃**。906 条受理命令全部完成；响应 P95/P99 为 3003.5/3004.7ms，最大 3012.8ms，符合默认数据库超时 3 秒及少量处理开销。队列和死信均排空。故障脚本在 stop 命令完成后等待 20 秒再 start，服务启动到可用另有时间，因此不可用窗口不等于恰好 20 秒。

复测发生在原长测数小时后，fixture 的滑动窗口自然推进；这里验证故障语义和恢复，不据此与原长测计算吞吐提升倍率。

## 超预算负载

最终修复版本在 100 RPS 输入下运行 60 秒，6000 次请求中 **1219 次 202、4781 次 429**，无其他 HTTP 错误、无调度丢弃。1219 条受理命令全部完成；成功请求 P95/P99 为 45.6/108.6ms，业务完成 P95 为 23ms。该受理数量符合每秒 20 加初始突发 20 的令牌预算。全部请求的混合延迟包含快速拒绝，不应拿它当成功写入延迟。

命令积压采样峰值 0、Outbox 峰值 2，结束排空。这里验证的是**超过预算时拒绝多余流量、保住已受理工作**，不是实现了 100 RPS 业务写入。

## 最终版本复测与收尾

过载后未重启服务，恢复至 20 RPS 连续运行 5 分钟：**6000/6000 全部受理并完成、零错误、零丢弃**；受理 P95/P99 为 52.6/105.2ms，业务完成 P95/P99 为 40/110ms；命令积压峰值 1，Outbox 峰值 2，结束排空。该次复测对应鉴权修复后的最终构建，不与早先不同时间窗口的数据比较提速倍数。

[最终数据核验](final-data-check.txt)：累计 50683 条命令全部为成功状态，对应 50683 条评论、50683 个唯一请求正文，无重复评论；预期评论通知 50666 条，实际也是 50666 条（不向自己发通知）。未完成命令、未发送 Outbox 均为零；[RabbitMQ 队列](final-queues.txt) 的 ready/unacknowledged 和死信均为零。[健康检查](final-health.txt) 正常，两个严格持久化参数保持 1，组提交延迟保持 0。

故障期间的 [压力告警与恢复日志](pressure-alerts.log) 和 [健康采样摘要](fault-health-summary.json) 一并保留。监控适配器已验证正常、降级、未知状态和连接失败分支；外部通知渠道未接入，也未发送消息。

Compose 配置校验、Python 脚本语法检查和修改文件的 `git diff --check` 通过。测试容器已停止，三个历史/当前压测数据卷与全部原始结果保留，没有部署生产。

本轮完成了保守运行档位验证、依赖停机恢复、过载保护和可供监控接入的告警信号。适合受控的小规模试运行；不代表生产规格、主机级高可用、多副本统一容量、断电恢复或长期内存稳定性已经验证。

```powershell
python -X utf8 scripts/capacity/run.py --scenarios async --rates 100 --duration 60s --label overload --output docs/capacity/2026-09-26-steady

```

工具拒绝覆盖既有结果；重跑需使用新的输出目录/标签并修改故障脚本的专用输出目录。故障脚本不可替换为生产配置。只有确认命令、Outbox 与 RabbitMQ 均排空，才开始下一个阶段。
