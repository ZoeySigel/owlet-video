# 架构与一致性

应用由 Next.js 静态前端、Gin API、Worker、MySQL、Redis 和 RabbitMQ 组成。API 与 Worker 共用代码和数据模型，以启动参数区分进程。媒体由 Nginx 或 Caddy 直接提供。

## 数据与事务

MySQL 是业务数据和排序快照的权威存储。`users` 用户名唯一，`invites` 在事务内加锁兑换，`sessions` 保存刷新令牌哈希和撤销状态，Redis 缓存短期 Session 租约；未命中回源自愈，撤销时写入标记，故障时等待旧租约退出。`likes` 和 `follows` 使用组合唯一索引，点赞数与评论数在事务中更新。

`feed_snapshots` 保存不可变的 `(video ID, score)` 数组和过期时间，按过期时间建立清理索引。点赞增加 `(created_at, video_id)` 索引，评论保留视频时间索引并增加时间索引，用于窗口聚合。启动时 GORM 增量建表和补索引，不删除既有字段；`popularity` 累计字段仍兼容保留，但不再作为热门 Feed 的依据。

## 排序与分页

最新和关注列表通过 Redis 缓存最近 1000 个 ID，热数据走详情三级缓存，超出范围拼接 MySQL 冷数据；按 ID 降序使用 keyset 游标，新发布的视频不会插入正在继续读取的旧页。关注关系变化仍会改变候选集合，不能将其称为关系快照。

热门和最多点赞按 `(score DESC, id DESC)` 生成不可变快照。热门分数为窗口内仍存在的点赞数 × 3 + 评论数 × 5，默认窗口 24 小时，时间边界为 `(生成时刻 - 窗口, 生成时刻]`。取消点赞、删除评论以及互动自然过期在下一次快照中反映；旧快照的顺序保持不变。Worker 每分钟重算，首屏请求也可按需生成。实时增量使用分钟 ZSET 分桶并按事件去重，作为辅助数据。权威快照在单条 SQL 内按视频聚合、排序并截取前 K 条，避免将窗口内全部分钟/视频组合搬到 Go 再写 Redis。它保留精确时间边界和无新消息时的自然过期，但每个新快照仍需一次 SQL 聚合。

快照按排序、配置和时间段生成确定性 ID。同一时间段的并发生成者通过 MySQL 唯一键收敛到先写入的版本。单进程合并生成请求，多进程可能各自执行聚合，但不会覆盖已发布的快照。

榜单默认只保留前 2000 条，可配置 20–10000 条。快照默认在所属分钟起算 15 分钟后到期，实际可翻页时间约 14–15 分钟。游标包含版本、排序、快照 ID、偏移及过期时间，使用 HMAC-SHA256 签名并校验排序，密钥使用 `JWT_SECRET` 且有独立签名域。每页 20 条，过期返回 HTTP 410 / `feed_cursor_expired`，前端重试会重新加载首屏。旧版热门/点赞游标同样提示重新加载。

快照写入 MySQL 后缓存至 Redis：元数据使用 `feed:snapshot:{ID}`，有序集合使用 `feed:rank:{ID}`。成员 ID 补齐 20 位，保证同分时数字 ID 的排序；实际分页读取 ZSET，并与持久化快照内容校验。Redis 不可用或丢失时读取 MySQL 快照，恢复后按需或由 Worker 重建缓存。返回的视频内容和计数仍为查询时的数据；快照保证顺序，不冻结视频详情。已删除的视频会跳过，因此单页可能不足 20 条。

这种 SQL 权威聚合与快照缓存不是无限规模的流式排名系统。窗口内事件量增长时，需要先观察查询计划和实际耗时，再考虑增量桶、分区或专用计算服务。

## 详情缓存与热点保护

- Redis 缓存正文使用 `video:v2:{ID}`，TTL 为 4 分钟加 0–119 秒随机抖动；不存在的视频缓存 20 秒。
- 进程内按视频和失效代次合并请求，最多容纳 1024 个在途键；调用者取消不会取消其他请求共享的回源。
- 跨实例使用 `SET NX` 重建锁，默认租期为数据库超时加 1 秒。令牌校验 Lua 原子回填并释放锁，旧持有者不能删除新锁。写操作失效时同时删除缓存与锁，撤销旧回填权限。
- 每个进程最多 12 个并发缓存回源/榜单构建任务。未取得锁时优先返回短期旧值，否则等待最多 600ms；仍没有缓存时返回 503，避免直接扩大数据库压力。
- 本地 LRU 最多 512 条，正常新鲜期 1 秒，正缓存最多保留 60 秒用于故障兜底；不存在的记录不能作为旧值兜底。返回旧值时带 `X-Cache: stale`。
- Redis 命令默认限时 200ms，详情数据库回源默认限时 3 秒。Redis 连续失败 3 次后熔断 2 秒，半开只放行一个恢复探测，恢复成功后自动闭合。

缓存提供最终一致性。进程间 L1 最多有 1 秒正常延迟；Redis 故障期间失效操作可能无法送达，恢复后已有旧缓存最迟随其 TTL 淘汰，不能宣称强一致。对外接口不应把缓存计数当作是否点赞的鉴权依据。

## 异步事件与恢复

发布的业务数据与 Outbox 同事务提交。互动请求先提交持久化命令和 Outbox，Worker 执行时将业务写入、命令结果和通知 Outbox 同事务提交。默认 API 等待消费结果，700ms 未完成或投递失败则锁定同一命令直写；`Prefer: respond-async` 成功投递后返回 202，可按命令 ID 查询结果。迟到 Worker 和 API 直写共享行锁及完成状态，不重复产生业务写入。Worker 等待 RabbitMQ Publisher Confirm 后标记 Outbox 已发送；崩溃窗口可能重复投递，属于至少一次投递。消费者在事务中写入 `processed_events` 唯一键和通知，实现通知副作用幂等，不能称为消息恰好一次。

消费采用固定 4 个 goroutine，每个预取 4 条。业务处理失败后延迟 10 秒重试，最多 3 次重试，随后进入死信队列；无效消息直接进入死信队列。RabbitMQ 连接或通道失败时，Worker 清理会话并按 1–30 秒退避加抖动重连，重建队列和消费者，继续发送数据库中的待处理事件。连接正常持续一分钟后，下次重连退避重置。

通知落库成功后，Redis 缓存失效和 Pub/Sub 提示按尽力方式执行。Redis 故障不会把已完成的通知错误地送入死信队列。SSE 建连立即发出刷新提示，此后每 20 秒刷新一次，并尽可能接收实时 Pub/Sub；即使提示丢失，也能从数据库补读。榜单维护独立于 RabbitMQ 会话运行。

## 可用性边界

登录与注册按 IP 和操作分别使用固定窗口限流：每小时最多 60 次登录、20 次注册，成功和失败请求都计数，从首次请求开始计时。正常使用 Redis Lua 限流，同时记录本地预算。Redis 不可用时使用同一进程的剩余预算，最多记录 10000 个键，容量满则返回 503；多实例降级期间不是全局统一限流，进程重启也会重置本地预算。需要多实例统一防护时应增加网关限流或独立可靠限流服务。

`/livez` 仅检查进程存活。`/healthz` 要求 MySQL 可访问；Redis 失败时返回 200 / `degraded`，MySQL 失败返回 503。该接口不表示消息队列正常，Worker 状态、队列积压和死信需要单独监控。

当前生产拓扑仍是单机：MySQL、RabbitMQ、媒体磁盘和主机均无副本故障转移。这里实现的是应用层超时、限流、降级和恢复，不代表集群高可用。数据库不可用时仅已缓存的详情可能继续读取，写入和数据库依赖列表仍会失败。上传文件、数据库和媒体需要一致备份。

## 新增能力与配置

互动限流、会话撤销、上传复用、软鉴权、可选双字段分页、启动脚本与独立 pprof 的完整说明见 [后端亮点对照](backend-highlights.md)。默认 pprof 关闭，启用后 API/Worker 分别只监听回环 6060/6061。改密会撤销全部会话，前端回到登录入口。

Outbox 发布每批最多 128 条，流水发送后核对全部 publisher confirm，再用单次数据库更新标记成功；有积压时连续读取，空闲时等待 100ms。确认关闭、NACK、路由退回或超时均保留整批待重试，由消费者幂等吸收重复。批次超时会关闭连接以中断 AMQP 库不响应 context 的阻塞写入。此流程仍是至少一次投递，并非消息恰好一次。

首屏在后台更新时可继续使用有效的上一份快照，但其生成时间距现在不得超过两个刷新周期（默认两分钟），且不能越过快照自身到期时间。该宽限仅降低刷新等待，不延长已签发游标期限。API 发布命令使用固定四路独立确认连接；Broker 确认后尝试标记命令 Outbox，标记失败仍由 Worker 重试。

MySQL 连接池保留最多 16 个空闲连接（最大连接上限仍为 16），空闲五分钟后回收。同步命令等待在 700ms 预算内逐步退避查询，从 40ms 增至最多 200ms，避免拥塞时反复轮询进一步增加数据库压力。

数据库初始化统一经 `openDatabase`。已知 UTF-8 字符集及排序规则默认启用驱动参数编码，减少一次性查询的 prepare/execute/close 往返；业务代码仍传递绑定参数。非 UTF-8 配置保留预处理，DSN 中显式设置 `interpolateParams=false` 可关闭此优化。不要自行拼接业务输入到 SQL。

评论响应复用同一事务中已锁定的用户和已插入的评论对象，时间戳与数据库毫秒精度对齐。命令执行保留本次生成的事件载荷供提交后缓存更新使用，不再重新查询刚写入的 Outbox；重复命令仍通过持久化事件修复缓存。载荷临时字段不进入数据库或 JSON 响应。
